# 交叉审查协议 v1

> 目的：两个独立审查方（Grok / Claude）在**事实层面**达成一致后，再由 Claude 落地修改。
> 状态：本文件由 Claude 维护。任一方要改规则，走 §12 的流程，不直接改本文件。

---

## 1. 角色与权限

| 角色 | 可读 | 可写 | 不可做 |
|---|---|---|---|
| **Grok**（外部审查方） | 仓库全部 | `reports/review/rounds/R<nn>-grok.md` | 改 `src/` `tests/` `config/` `scripts/`、改 `LEDGER.md`、改本文件 |
| **Claude**（实现方） | 仓库全部 | `src/` `tests/` `config/` `scripts/`、`rounds/R<nn>-claude.md`、`LEDGER.md` | 改 Grok 的轮次文件 |

**文件所有权是硬规则**：任何一方只写自己的文件。这样两方交替 push 永远不会产生 merge 冲突，不需要处理 rebase 冲突之外的情况。

---

## 2. 每轮的文件流

```
Claude  更新 LEDGER.md（列出本轮待回应条目）→ commit → push
Grok    git pull --rebase
        新建 rounds/R<nn>-grok.md（只针对待回应条目 + 新增发现）→ commit → push
Claude  git pull --rebase
        新建 rounds/R<nn>-claude.md（逐条判定 + 复现输出）
        更新 LEDGER.md → commit → push
Grok    ...重复，直到 LEDGER 无「存疑」
```

轮次编号 `nn` 从 01 开始，双方同步递增。

---

## 3. 一条发现的固定格式

每条发现必须完整包含下面 6 个字段，缺任何一个视为无效条目，直接退回：

```markdown
### G-01 停牌日仍用当日收盘价估值

- 主张：一句话，陈述可被推翻的事实，不写"可能"。
- 证据：`src/a_share_quant/backtest/engine.py:271-275` + 该行代码原文
- 复现：最小断言 + 预期结果（例如"停牌日 OHLC 翻倍后，日收益应≈0，实际 -49.95%"）
- 失败场景：什么数据、什么参数下会出错，造成什么方向的偏差
- 严重度：高 / 中 / 低
- 撤回条件：什么情况下这条不成立
```

---

## 4. 判定词表

| 判定 | 含义 | 后续动作 |
|---|---|---|
| **成立** | 可执行断言复现成功，方向与主张一致 | 进修复清单 |
| **条件成立** | 只在特定数据/配置下成立，须写清前置条件 | 进修复清单 + 限制清单 |
| **不成立** | 与代码事实不符，须附 `file:line` 反证 | 关闭 |
| **存疑** | 现有数据无法判定 | 最多保留两轮，之后转「待真实数据」 |
| **待真实数据** | 必须真实行情才能验证 | 写入 README 限制清单，不阻塞修复 |

判定只由 Claude 在 `rounds/R<nn>-claude.md` 与 `LEDGER.md` 中写入。Grok 可以不同意，但必须给出**新的可证伪断言**才触发复核。

---

## 5. 事实与优先级分离

- 只对「事实判定」求一致；
- 严重度与修复顺序由**用户**拍板，不作为共识条件；
- 因此"我认为这是高危" vs "我认为是中危" 不构成分歧，不需要争论。

---

## 6. 版本锚定（防幽灵争议）

- 每条发现必须写 `reviewed_commit: <sha>`；
- 引用行号时**必须附该行代码原文**——行号会漂移，原文不会；
- 若 `HEAD` 已前进，写之前先 `git log --oneline -5` 比对，并注明"该行在当前 HEAD 是否仍存在"；
- 基于旧 SHA 的报告，若对应代码已改动，条目状态记为 `stale`，不进入判定。

---

## 7. 停止规则

1. 最多两轮正式交锋；
2. 第三轮只处理带 `blocking` 标记的条目；
3. `LEDGER.md` 中「存疑」清零即视为达成一致；
4. 两轮后仍存疑 → 转「待真实数据」，写入限制清单，不再讨论。

---

## 8. 提交协议

- commit message：`review: R<nn> <角色>`，正文列条目编号；
- push 前必须 `git pull --rebase`；
- 一次提交只包含本轮自己那个文件（Claude 可附带 `LEDGER.md`）；
- 禁止 force push；
- 禁止修改对方的轮次文件。

---

## 9. 共识的定义

同时满足以下四条才算"达成一致"：

1. `LEDGER.md` 中每条 `F-*` 都有明确判定；
2. 不存在 `存疑`；
3. 修复清单确定：条目 → 改动范围 → 完成判据；
4. 用户确认优先级。

只有到这一步，Claude 才开始改代码。

---

## 10. 禁止事项

- 不复述已关闭的条目；
- 不凭记忆引用行号，必须重新读文件；
- 不把"建议改法"当作争议内容（改法由实现方定，可写成附注）；
- 不用"可能/大概/或许"描述缺陷：要么给断言，要么标存疑；
- 不评价对方的动机或能力，只针对代码与断言。

---

## 11. 首次任务（给 Grok）

1. `git pull`，确认 `HEAD`；把 SHA 写进 `R01-grok.md` 的头部；
2. 审查 `reports/fix_log.md` **第八节**列出的第二轮修复是否真的修对了（重点是"修完之后是否引入新问题"）；
3. 对 `LEDGER.md` 中 `F-01`～`F-06` 六条待判定项表态：接受现状 / 补充证据 / 认为定级有误（定级不作为争议，只需一句话）；
4. 提出你认为**新增**的发现，按 §3 格式，编号续 `F-07` 起；
5. 不要把已修复的历史问题重新列为发现。

---

## 12. 规则变更

任一方在轮次文件里写 `## 规则变更提议` 段落，说明改哪条、为什么。
另一方在下一轮回复 `同意` / `反对 + 理由`。双方同意后，由 Claude 修改本文件并把 `v1` 递增。

---

*本协议只管审查流程，不涉及投资建议。回测结果不代表未来收益。*
