## F-26 对账把同一笔成交再记一遍，退出码 2 之前已经写盘

**判定：成立**（Grok 评"中"，我认为在实盘层这是最高优先——理由见下）。

### 复现（本机实测，临时目录 `_dstest/r06/`，不写 `live/`）

起始持仓 `000001 = 1000`，委托买入 100、成交 100：

```
第 1 次：--holdings h0.csv(1000) --save-holdings h1.csv  →  h1 = 1100，退出码 0
第 2 次：--holdings h1.csv(1100) --save-holdings h2.csv  →  h2 = 1200，退出码 0
```

**两次都退出码 0，股数累加了一遍**。Grok 的撤回条件是"第二次运行时股数不再增加"，
实测不满足。

超量场景（委托 100、成交 300）：

```
退出码 = 2，但持仓文件已写成 000001 = 1300
```

即 `critical` 判定在写盘之后——报警挡不住落盘，而且入的是**成交数 300**，
不是委托数 100。操作者看到退出码 2 之后若再执行同一条命令，会再从 1300 往上加。

### 证据（行号对应 `baae4a8`）

`scripts/reconcile.py:199-205`：

```python
    if args.save_holdings:
        p = Path(args.save_holdings)
        p.parent.mkdir(parents=True, exist_ok=True)
        pd.DataFrame({"symbol": list(new_holdings),
                      "shares": list(new_holdings.values())}) \
            .to_csv(p, index=False, encoding="utf-8")
```

`scripts/reconcile.py:208-211`（在上面**之后**）：

```python
    # 超卖/超量/对不上单属于必须人工处理的问题，用非零退出码让脚本链能感知
    critical = (summary["n_over"] > 0 or len(unmatched) > 0
                or any("超过持仓" in w for w in warn_hold))
    sys.exit(2 if critical else 0)
```

`src/a_share_quant/live/reconcile.py:176`：

```python
            pos[sym] = pos.get(sym, 0) + sh
```

没有"这批成交已经入过账"的标记。

### 为什么我认为它比"中"更靠前

`--save-holdings` 的典型用法是 `live/holdings.csv`——**次日建仓的输入**。
重复入账不会报错，只会让第二天的组合按错的持仓算，而且错得很隐蔽
（多出来的股数看起来像"昨天买到了"）。这条的危害不在当次，在次日。

## F-28 首次持仓日净值仍等于初始值时，两条暖机切点不同

**判定：成立**，但**条件成立**——需要"零成本 + 成交日收盘净值仍等于初始资金"同时满足。

### 复现（本机探针 `_dstest/r06/probe_warmup.py`）

9 个交易日，前 6 天净值恒为 1,000,000，第 7 天起涨。持仓表给出"第 3 天就有持仓"：

```
持仓路径: warmup=1  起点=2024-01-03  长度=8
平盘路径: warmup=5  起点=2024-01-09  长度=4
分叉: True
```

对照组（首次持仓日净值已离开初始值，第 7 天持仓）：

```
持仓路径: warmup=5 起点=2024-01-09 | 平盘路径: warmup=5 起点=2024-01-09  分叉=False
```

### 证据

`src/a_share_quant/metrics/performance.py:255-268`，持仓表路径优先，
`if start is None:` 之后才走平盘路径——持仓表一旦给出切点，净值是否平坦就不再参与判断。

**为什么默认成本下不触发**：默认 `CostModel` 的最低佣金 5 元会在成交日把净值打离
初始值（Grok 的引擎对照里是 999250.6251250001），两条路径随即重合。
所以**已发布的三段数字不受影响**，这也是我判定为"条件成立"而非"成立（无条件）"的原因。

Grok 另验了一件我原本担心的事：全程平盘被持仓路径截短时，年化仍是 0.0、Sharpe 0.0，
**不是 NaN**——任务书里"指标全 NaN"的担忧没有发生。

## F-29 没有持仓表时 first_active_date 报的是仍等于初始资金的那一天

**判定：成立**。

### 复现（本机探针）

```
报出的 first_active_date = 2024-01-05，该日净值 = 1,000,000（仍等于初始资金）
```

## F-31 完全未成交时，费用和滑点比率写成 NaN

**判定：成立**。

### 复现（本机实测）

委托买入 100、成交文件为空、持仓 1000：

```
退出码 0，标准输出含「加权滑点 +nanbp」「费用 0 元（nanbp）」
reconcile.json:  "fee_bps": NaN,
                 "weighted_slip_bps": NaN,
```

严格 JSON 解析（`json.loads(..., parse_constant=抛出)`）：

```
严格模式: 拒绝 -> 非标准 JSON 常量: NaN
```

Python 自带的 `json.load` 默认**容忍** NaN，所以这个问题在本项目内部不会报错，
但文件一旦被别的解析器读（JS 的 `JSON.parse`、R 的 jsonlite）就会失败。

### 证据

`src/a_share_quant/live/reconcile.py:238` 的函数说明：

```python
    """汇总指标。所有比率在分母为 0 时返回 0，不返回 NaN 混进报告。"""
```

与 242 / 258-266 行的实际实现相反：

```python
        slip_bps = fee_bps = float("nan")
        ...
        slip_bps = (...  if notional > 0 else float("nan"))
        fee_bps = (total_fee / notional * 1e4) if notional > 0 else float("nan")
```

**说明与实现自相矛盾**，这是我认为必须修的直接理由——不是"NaN 不好看"，
而是有人照着说明写了下游解析代码。Grok 的撤回条件（"未成交时这两个键是 0 或 null"）
实测不满足。
