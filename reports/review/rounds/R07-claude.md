## 1. F-32：洞 ③（本轮最有价值的产出）

**他说中了本质**：`_fills_digest` 吃的是 `normalize_fills` **之后 DataFrame 的列布局、
dtype 和行数**，不是成交内容本身。我原以为 normalize 会吸收格式差异，它只吸收了
**值的写法**（空格、`10.0`/`10.00`、`证券买入`、行序），没吸收**结构**。

本机复现（基线 h1 = `000001,300 / 600000,1100`，拿 h1 重跑同一批成交的另一种写法）：

| 写法 | exit | 结果 |
|---|---|---|
| 列顺序换成 `side,symbol,price,shares,fee` | 0 | `000001,100 / 600000,1200` |
| 多一列 `trade_id` | 0 | 同上 |
| 去掉 `fee` 列 | 0 | 同上 |
| `fee` 写成 `5`（整列 int64） | 0 | 同上 |
| 明细化：600000 拆成 60+40 两笔 | 0 | 同上 |

五种全部 exit=0 且股数加倍，**与他报告逐位一致**。

**为什么这条我自己想不到**：我写 digest 时的心智模型是"同一批成交 = 同样的
股票/方向/股数/价格"，我测的全是这个模型内的扰动。而真实场景的破坏方式是
**换导出模板**——当天用客户端「当日成交」导出（无 fee、明细粒度），次日拿
「交割单」再对一遍（有 fee、多出成交编号、列顺序不同、汇总粒度）。这在我的模型之外。

**buy 和 sell 不对称**（他指出的这点很关键）：买入重复永远不会触发 `critical`，
静默多记；卖出重复只有在超过持仓时才被拦（exit 2），持仓以内的卖出重复静默少记。
后果方向相反——多记让次日少买或下卖不出去的单，少记让次日多买、引发现金不足告警。

**修法我接受他给的**，但要加一条约束：**聚合会丢 fee，而 fee 参与费用对照**
（`_model_fee` 与实收对照）。所以指纹用聚合后的四列，**费用对照仍必须用原始
`fills`**——这两件事要取不同的数据，不能因为改指纹就把 fee 一起丢了。

- 撤回条件：五种写法在修完后重跑得 exit=1 且持股不变。

## 2. F-33：保护本身会造成数据错误

这条比 F-32 更反直觉，也是我在任务书里写"误伤比漏拦更糟"时没想到具体形态的：

- **(a) 连续两天全部未成交**：第 1 天写 digest=`empty`，第 2 天同样的空成交被判
  "已入过账" → exit=1，拒绝写出 e2。空批次**本来就没有可重复入账的股数**，这次拦截
  纯属误伤。链式脚本里 e2 不存在，下一步读不到文件。
- **(b) 同日两批内容恰好相同**（委托 200 股分两次各成交 100 股 @10.00、各 5 元佣金）：
  第 2 批被拦 → **少记 100 股**。

本机两条都复现，数字与他一致。

**(b) 的方向值得单独说**：不拦不会多记（两批都是真成交），**拦了反而少记 100 股**。
也就是说这个保护在合法用法下会自己制造数据错误。

**(a) 最危险的地方是引导用户自废保护**：调仓日挂单因涨停/停牌全部没成交，次日继续
挂、继续没成交——这是很常见的两天。提示写着"确认要重跑就先删掉 digest"，用户照做，
这份持仓的保护就没了，下一次真重跑时洞 ② 被系统引导出来。

**修法**：① 空批次不查、不写指纹（这条无争议）；② 非空批次改**日期 + 指纹双键**，
跨天不拦；③ 同日内内容相同的合法分批无法从数据本身区分，所以解除方式**不能是
"删 digest"**，要给显式的 `--force`（"我知道这是另一批真实成交"），删文件等于废保护。

## 3. F-34：我修 critical 时漏掉的另一条写盘路径

R06 我把 `critical` 判定前移到写盘之前，但**只管了 `save_holdings` 那一处**。
报告写盘（214–222 行）在指纹拦截（241 行）**之前**，被拦时照样写，且覆盖正确版本。

`n_holdings_diff`→2、`abs_value_gap`→3300.0。**与他报告逐位一致**。

**为什么这条比看上去严重**：持仓文件是对的，但给人看的"结果偏差"报告（模块说明
把它列为**最重要**的一项）被改成一份**并不存在的偏离**，第一次的正确报告被覆盖、
无法恢复。操作者事后翻报告，会看到每只都"偏离一手"，然后去查一个不存在的问题。
这是我上一轮"critical 前移"只做了一半的证据——**我改的是我想到的那一处写盘，

## 6. 对 §4 结项判断的回应

他答"**能但要带条件**"，6 条。**我接受**，并补两条：

**① 他的条件 5（每周用券商持仓导出逐只核对股数）是最重要的一条，而不是附带项。**
指纹只防"同一批成交被再对一次"这一种错误。真实世界的错误它一个都防不住：
改单、分红送股、对账时漏了一笔、券商回报延迟。这一条才能兜住整类问题，
包括洞 ① 和 F-32/F-33 的所有残余。8 周内每周一次，成本极低。

**② 修 F-32 时不能把 fee 一起丢掉**（见 §1）。指纹用聚合后的四列，
费用对照仍用原始 `fills`。

另外他的条件 6（每次调用都要检查退出码，链式脚本遇非 0 必须停下）我完全同意——
0 正常、1 重复未写持仓、2 人工处理未写持仓，这套退出码语义现在要写进
`reports/live_readiness.md` 的每日流程里，否则纸面上有、操作上没人看。
