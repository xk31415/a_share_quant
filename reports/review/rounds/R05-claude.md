## F-16 首次持仓日的收益不进年化 —— **成立**

**证据核对**：`performance.py:253-254` 取 `dates.min()`（首个 `shares > 0` 日），
`267` `trimmed = eq[eq.index >= start]`，`30` 用首尾之比算年化。所以 `start` 当天的
收益 `eq[t]/eq[t-1]-1` 落在序列之外，而 `cumulative_return` 用 `eq_full`，把它算进去了。

**Grok 证据里有一句不准确**：它写"有持仓表的分支没有这道长度判断"。实际上
`268-269` 的 `if len(trimmed) < 2: return eq, 0` 对两个分支都生效；没有的是
`n_flat >= 2` 那个**平盘长度**启发式（本来就不该用于持仓分支）。这条不影响判定。

**我补的量（Grok 标为"无法判定"的那一格）**：

| 段 | 首次持仓日 | 该日收益 | 现年化 | 补回前收当天后 | 差 |
|---|---|---|---|---|---|
| 2020-2024 | 2020-05-06 | **+2.0388%** | 9.3256% | 9.7997% | **+0.47pp** |
| 2015-2019 | 2015-05-04 | **+1.2963%** | -13.7516% | -13.4837% | **+0.27pp** |
| 2025-2026 | 2025-05-06 | **+1.9224%** | 3.8823% | 5.2695% | **+1.39pp** |

三段首次持仓日都恰好是 **4 月最后一个交易日之后、5 月第一个交易日**，且当天都涨
1.3%~2.0%——这不是巧合，是"季初建仓"的建仓日效应，被系统性地从年化里删掉了。
2025-2026 段最吃亏（+1.39pp），因为它样本最短（355 个有效交易日），一天占的比重最大。

**旁证（同一 bug 的另一个出口）**：`cumulative_return_active` 是 0.4926（2020），
而 `cumulative_return` 是 0.5230，比值 1.5230/1.4926 = 1.0204，正好等于那天的 +2.04%。
说明 `*_active` 也漏同一天。

**修法（实现建议，不作为争议）**：`trim_warmup` 的切点前移一个净值点——用
`first_inv` 在 `eq_full` 里的**前一个**交易日做基准点，而不是 `first_inv` 本身。
这样当天收益进入 `pct_change` 的第一个值，`warmup_days` 从 79 变 78（2020）。
`first_active_date` 仍报首次持仓日，不要把基准点当成 active 起点。

**为什么这条必须先修**：它是唯一一条会**改写已发布数字**的条目，而且方向和
"撤回样本外失效"那轮修正相反——上一轮把超额抬起来，这一轮还要再抬高一点。
两轮改完再定的口径才是可引用的；现在引用的 9.33 / -13.75 / 3.88 都偏低。

## F-17 开头的主动空仓被当成暖机删掉 —— **条件成立**

代码事实成立：`trim_warmup` 只认"净值开头连续等于初始值（≥2 天）"或"还没有
`shares > 0`"，不区分这段空仓来自 `min_list_days`（不可控）还是策略选择（可控）。

**判"条件成立"的理由**：对当前三段等权回测，开头空仓确实全部来自股票池预热，
删掉是对的，所以已发布的等权数字不受影响。只有当我们真的做一个"开局空仓"的
择时策略时，这条才有害——那正是 Grok 的复现构造（前 10 天平盘、基准 +2%/天，
全序列超额 -3.71pp、截断后 -2.52pp）。

前置条件写清：**开头空仓期内基准有涨跌，且该空仓是策略主动选择**。

**它和 F-16 是同一个根**：截断规则无法区分"池子为空"与"选择空仓"。真正该用的
判据是**"策略第一次可能持仓的那天"**（股票池非空且当日可交易），不是"第一次真的
持仓那天"。这个改动比 F-16 大，涉及把 universe 的可交易信息带进指标层，建议分开做。

## F-18 `*_active` 与 `n_cash_only_days` 截断后失效 —— **成立**

`326` 先把 `eq` 换成截断序列，`365-370` 又在这个 `eq` 上算 `first_inv` 与
`(eq.index < first_inv).sum()`。而截断起点就是 `first_inv`，所以这个 sum 恒为 0。

实测三段：`warmup_days` = 79 / 78 / 78，`n_cash_only_days` = **0 / 0 / 0**，
`annualized_return_active` 与 `annualized_return` **完全相同**（9.3256 / -13.7516 / 3.8823）。
`*_active` 现在是主口径的复制品，既不提供信息，又和 README 第 13 条
（"默认全区间，汇报时优先用 `*_active`"）矛盾——第 13 条描述的是改之前的行为。

两种修法，取其一（实现建议）：删掉 `*_active` 整组字段并在 README 13 条写"已并入
主口径"；或让 `*_active` 在 `eq_full` 上算，保留"全区间 vs 有效区间"两套。我倾向前者——
两套口径同时存在正是上一轮口径混乱的来源。

## F-21 补位越过取价窗口就整张计划报错 —— **成立**

`live_signal.py:226` 只取 `ranked[:max(n*3, 300)]` 加上持仓；`Sample.active` 沿完整
`ranked` 补位；`size_positions` 在缺价时 `raise ValueError`。

我的复现（`ranked` 400 只、`n=100`、前 250 不可投资、只有前 300 有价）：

```
picked 末位: 000349 | 有价的: False
抛出: ValueError 缺少有效价格：['000300', '000301', '000302', '000303', '000304']
```

触发条件是"前 3n 名里不可投资比例 > 2/3"，听着极端，但停牌潮（2015 那种）或
大面积 ST 时完全可能。**后果是当天不出单**，比出错的单更糟——它静默变成"今天没信号"。

## F-22 `benchmark.csv` 丢掉前导零后指纹不变 —— **成立**

我直接验：

```
a.csv (000852): symbol=852 dtype=int64 digest=12f6f5638dcf
b.csv (852)   : symbol=852 dtype=int64 digest=12f6f5638dcf
两者指纹相同? True
```

`load_table` 里的 `pd.read_csv(path)` 没有 `dtype`，`symbol` 被推断成 int64。
后果：一份把 `000852` 写成 `852` 的坏数据能通过校验。

**修法有个必须一起做的动作**：`load_table` 加 `dtype={"symbol": str}` 之后，
已入库的 `data/MANIFEST.json` 里 `benchmark.csv` 的指纹会**立刻全部失配**
（因为旧指纹是拿 int64 算的）。所以这条不能单独修，必须"改代码 + 重新 `write`"
同一个提交，否则别人 pull 下来 `verify` 全红。

严重度我记 Grok 的"中"，但实际危害比它低——`benchmark.csv` 只有一列 symbol，
坏掉的前提是数据源自己写坏；`bars.parquet` 走 parquet 不受影响。
